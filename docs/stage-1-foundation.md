## 0. Purpose of this document

This is the blueprint we sign off on **before** writing code. It fixes the decisions that are expensive to change later: repository layout, how services talk to each other, how identity and permissions work, how the database evolves, and how money and time are represented. Everything in Stages 2–8 plugs into the seams defined here.

The guiding test from the master prompt applies to every decision below:

> "Will this still make sense when Heissal has hundreds of bookings, multiple sales agents, multiple vehicles, hundreds of accommodation rates, thousands of clients and eventually a mobile app?"

Nothing here hard-codes tourism business rules. Stage 1 builds the *chassis*; the pricing/park-fee/rate data all arrives as configuration in Stage 2.

## 1. What Stage 1 delivers (definition of done)

Stage 1 is complete when an engineer can clone the repo and, with a single command, bring up a system where:

1. `docker compose up` starts PostgreSQL, Redis, the FastAPI API, and the Next.js admin app.
2. The API exposes `GET /api/v1/health` returning `{"status":"ok","db":"ok","redis":"ok"}` and serves OpenAPI docs at `/docs`.
3. Alembic migrations create the initial schema (users, roles, permissions, role/permission links, audit_log, and supporting tables) and are applied automatically on startup in dev.
4. A seeded superuser can log in via `POST /api/v1/auth/login`, receive access + refresh tokens, and call a protected endpoint.
5. RBAC is enforced: a request without the right permission returns `403`; without auth returns `401`.
6. The admin app renders a login screen, authenticates against the API, and shows a protected admin shell (sidebar + top bar + empty dashboard + a working Users/Roles admin page backed by the API).
7. CI (GitHub Actions) runs lint, type-check, and tests on every push, and they pass.
8. Every mutating action writes an audit-log row (who, what, when, before/after).

Acceptance criteria are enumerated in §12. Until they are all met and *verified by running*, Stage 1 is not "done" — per the project's execution loop.

## 2. Technology decisions (and why)

The master prompt fixes most of the stack. This section records the specific choices within it and the few additions the foundation needs.

**Backend:** Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), PostgreSQL 16, Alembic (migrations), Redis 7 (cache/session/queue), `uv` for dependency + venv management (fast, reproducible lockfile). Password hashing with **Argon2id** (`argon2-cffi`). JWT via `pyjwt`. Async Postgres driver `asyncpg`.

**Frontend:** Next.js 15 (App Router), TypeScript, React 19, Tailwind CSS, shadcn/ui, React Hook Form, Zod, TanStack Query. Package manager **pnpm** with workspaces.

**Monorepo orchestration:** pnpm workspaces for the JS side + **Turborepo** for task pipelines/caching. Python (`apps/api`) is managed by `uv` and invoked through Turbo/Make wrappers so `make lint`/`make test` work uniformly.

**Infra:** Docker + Docker Compose for local dev. Object storage, email, payments, maps, and exchange-rate providers are defined as **abstract interfaces** now (empty/stub implementations) so later stages implement them without touching call sites.

**Money:** stored as PostgreSQL `NUMERIC(18,4)` and handled as Python `Decimal` end-to-end. **Never floats.** Currency is always stored alongside the amount (ISO 4217 code). This is a foundation rule because the pricing engine's correctness depends on it.

**Identifiers:** primary keys are **UUID v7** (time-ordered, index-friendly, safe to expose, mobile/offline-friendly). Human-facing business identifiers (e.g. quote number `HTQ-2026-00001`) are separate columns generated by their own service. We do not expose auto-increment integers.

**Time:** all timestamps stored as `TIMESTAMPTZ` in UTC. Display/timezone conversion happens at the edge. Business timezone default: `Africa/Nairobi`, configurable.

> Rationale notes for the two additions not named in the brief: `uv` and Turborepo are tooling accelerators, not architectural commitments — they can be swapped without affecting application code. UUID v7 and the money/decimal rule are architectural and are chosen for correctness and scale.

## 3. Repository layout (monorepo)

Polyglot monorepo: one Python service today, multiple TypeScript apps and shared packages, room for background workers.

```text
heissal/
├── apps/

│   │   ├── app/
│   │   │   ├── main.py         # app factory, router registration, middleware
│   │   │   ├── core/           # config, security, logging, deps, errors
│   │   │   ├── db/             # engine, session, base model, mixins
│   │   │   ├── modules/        # one folder per domain (modular monolith)
│   │   │   │   ├── auth/       # login, refresh, password, tokens
│   │   │   │   ├── users/      # user CRUD, profile
│   │   │   │   ├── rbac/       # roles, permissions, assignment, guards
│   │   │   │   └── audit/      # audit-log model + writer service
│   │   │   ├── integrations/   # abstract provider interfaces (email, storage,
│   │   │   │                   #   payments, maps, fx) + stub impls
│   │   │   └── api/v1/          # versioned router assembly
│   │   ├── alembic/            # migration environment + versions/
│   │   ├── tests/              # pytest (unit + integration)
│   │   ├── pyproject.toml
│   │   └── Dockerfile
│   ├── admin/                  # Next.js internal admin/sales dashboard (Stage 1 shell)
│   ├── web/                    # Next.js public website (Stage 6 — stub only now)
│   └── portal/                 # Next.js client portal (Stage 7 — stub only now)
├── packages/
│   ├── api-client/             # TS client generated from the API's OpenAPI schema
│   ├── ui/                     # shared shadcn/ui components + Tailwind preset
│   ├── config-eslint/          # shared eslint config
│   └── config-tsconfig/        # shared tsconfig bases
├── infra/
│   ├── docker/                 # supporting Dockerfiles, entrypoints
│   └── compose/                # docker-compose overrides (dev/test)
├── docs/                       # design docs (this file lives here in-repo)
├── .github/workflows/          # CI pipelines
├── docker-compose.yml
├── turbo.json
├── pnpm-workspace.yaml
├── Makefile                    # unified entrypoints: make dev/lint/test/migrate
└── README.md
```

**Why three separate Next.js apps** (`admin`, `web`, `portal`) instead of one: they have different audiences, auth models, deploy cadences, and risk profiles (the public site is anonymous and SEO-driven; the admin app is authenticated and internal; the portal is authenticated client-facing). Keeping them separate but sharing `packages/ui` and `packages/api-client` gives clean separation without duplication. Only `admin` is built in Stage 1; `web` and `portal` are created as minimal stubs so the workspace graph is complete and later stages have a home.

**Why the modular monolith on the backend:** each Stage 2+ domain (clients, destinations, accommodations, pricing, quotes, itineraries, leads, bookings, payments, operations) becomes a self-contained folder under `app/modules/` with its own `models.py`, `schemas.py`, `repository.py`, `service.py`, `router.py`. Business logic lives in `service.py` (never in routers, never in the frontend). If a module ever needs to become its own service, the seam is already there.

## 4. API architecture

**Style:** REST over HTTP/JSON, versioned under `/api/v1`. OpenAPI generated automatically by FastAPI; the TS `api-client` package is generated from that schema, so the website, admin, portal, and future mobile app all consume the *same* typed contract. This is the concrete mechanism behind the brief's "one backend, many clients."

**Standard conventions fixed now** (so every later module is consistent):

- **Error envelope:** all errors return `{"error": {"code": "STRING_CODE", "message": "...", "details": [...]}}` with correct HTTP status. Internal details are never leaked to clients (master prompt §42, §9).
- **Pagination:** list endpoints accept `?limit=&cursor=` (cursor-based, stable under inserts) and return `{"items": [...], "next_cursor": "..."}`.
- **Auth:** `Authorization: Bearer <access_token>`. Access token ~15 min; refresh token ~7 days, rotated on use, revocable via Redis deny-list.
- **Validation:** every request/response is a Pydantic model. Unknown fields rejected. Money fields validated as Decimal with currency.
- **Idempotency:** mutating endpoints that will later touch payments accept an `Idempotency-Key` header (wired now, enforced where it matters later).
- **Rate limiting:** middleware backed by Redis (per-IP for auth endpoints from day one).

**Health & ops:** `/api/v1/health` (liveness + dependency checks), `/metrics` seam for later, structured JSON logging with request IDs.

## 5. Data model — Stage 1 tables

Stage 1 only creates the identity/authz/audit core. Business tables arrive in their stages. All tables get `id UUID PK`, `created_at`, `updated_at` (TIMESTAMPTZ), and — where they represent user-editable business data — `created_by`, `updated_by`, and soft-delete `deleted_at`.

```text
users
  id, email (unique, citext), full_name, hashed_password,
  is_active, is_superuser, last_login_at, created_at, updated_at

roles
  id, key (unique, e.g. 'sales_agent'), name, description, is_system

permissions
  id, key (unique, e.g. 'quote:create'), description

role_permissions      (many-to-many)
  role_id, permission_id

user_roles            (many-to-many)
  user_id, role_id, assigned_by, assigned_at

refresh_tokens        (or Redis-backed; table for auditability)
  id, user_id, token_hash, expires_at, revoked_at, user_agent, ip

audit_log
  id, actor_user_id, action (e.g. 'PRICE_OVERRIDE'), entity_type,
  entity_id, old_value (jsonb), new_value (jsonb), ip, created_at

app_settings          (key/value config seam for later stages)
  id, key (unique), value (jsonb), updated_by, updated_at
```

**Permission model:** RBAC with fine-grained permissions grouped into roles. Permissions are strings shaped `resource:action` (`quote:create`, `quote:approve_discount`, `pricing_rule:edit`, `user:manage`). Roles are permission bundles. This scales to the many roles the platform needs (admin, sales_agent, operations, finance, viewer, and later a `client` role for the portal) without code changes — new permissions are seeded via migration, assigned via the admin UI.

**Seeded roles for Stage 1:** `superadmin` (all permissions), `admin`, `sales_agent`, `operations`, `finance`, `viewer`. Exact permission-to-role mapping is data, editable in the admin UI and captured in a seed migration.

**app_settings** exists from Stage 1 so that Stage 2's "administrators change business data without developers" (master prompt §44) has a home for global config (default currency, quote validity days, markup defaults, fuel price, tax) — each of these becomes either a settings key or a dedicated configurable table in its own stage.

## 6. Authentication & authorization design

**Authentication:** email + password. Passwords hashed with Argon2id (tuned work factor). Login issues a short-lived access JWT (signed HS256 in dev, RS256-ready for prod) and a rotating refresh token. Refresh tokens are hashed at rest and revocable (logout, password change, admin revoke) via a Redis deny-list keyed by token ID. Failed-login rate limiting on the auth endpoints.

**Authorization (RBAC):** enforced in the backend via FastAPI dependencies:

```python
@router.post("/quotes", dependencies=[Depends(require_permission("quote:create"))])
```

`require_permission` resolves the current user from the token, loads their effective permissions (roles → permissions, cached in Redis per session), and returns `403` if the permission is absent, `401` if unauthenticated. Permissions are checked **server-side only**; the frontend uses the same permission list to show/hide UI but never as a security boundary.

**Audit:** a single `AuditService.record(actor, action, entity, old, new)` is called from service-layer mutations. Stage 1 wires it for user/role changes; later stages call the same service for price overrides, discount approvals, quote sends, etc. (master prompt §45).

**Client portal note:** portal users (Stage 7) are the same `users` table with a `client` role and a link to a `clients` record. The auth core is built once here to serve both staff and clients — no second auth system later.

## 7. Database migrations

Alembic manages all schema. Rules fixed now:

- Every schema change ships as a reviewed migration file in `alembic/versions/`. No manual production DDL (master prompt §8, §43).
- Autogenerate is used as a starting point, then hand-reviewed (autogen misses enums, indexes, data migrations).
- Seed data (permissions, system roles, superuser bootstrap) ships as explicit data migrations or an idempotent seed script, so a fresh environment is reproducible.
- In dev, migrations run automatically via the API container entrypoint before the app starts. In CI/prod they run as an explicit deploy step.
- A `make migrate` / `make makemigration name=...` wrapper standardizes the workflow.

Testing runs against a real PostgreSQL (matching prod), created and torn down per test session, so migrations themselves are exercised.

## 8. Admin shell (Stage 1 frontend)

The `admin` Next.js app in Stage 1 is deliberately thin but real (no fake "coming soon" buttons — master prompt §47):

- **Login page** → calls `POST /api/v1/auth/login`, stores tokens (httpOnly cookie via a Next.js route handler; not localStorage), redirects to dashboard.
- **Authenticated layout:** persistent sidebar + top bar + content area, responsive (mobile-friendly per §49), built from `packages/ui` (shadcn/ui). This layout is the frame every Stage 2+ admin screen drops into.
- **Dashboard page:** empty-state scaffold with the KPI tiles named in §41 shown as placeholders wired to a real (initially zero-value) endpoint — structure real, data arriving in later stages.
- **Users & Roles admin:** a genuinely working CRUD screen — list users, create user, assign roles, view/edit role permissions — backed entirely by the API. This proves the whole vertical slice (Next → TanStack Query → typed api-client → FastAPI → RBAC → Postgres → audit) end-to-end.
- **Auth guard + permission-aware nav:** routes redirect to login when unauthenticated; nav items hide based on the user's permissions (mirroring, not replacing, server checks).

Data fetching uses TanStack Query against the generated `api-client`; forms use React Hook Form + Zod (Zod schemas shared where possible with the API contract).

## 10. Cross-cutting foundations set in Stage 1

- **Config:** `pydantic-settings`, all secrets from environment, `.env.example` committed, real `.env` never committed. Secret-management seam for prod.
- **Logging:** structured JSON logs with request/correlation IDs; no sensitive data in logs.
- **Error handling:** global exception handlers map domain errors → safe client responses; unexpected errors → generic 500 with logged trace.
- **Security baseline (master prompt §42):** CORS locked to known origins, security headers, input validation everywhere, rate limiting on auth, least-privilege DB user, no internal cost/margin fields ever serialized to non-authorized roles (enforced via response schemas per audience — the internal-vs-client separation from §20 is a schema-level rule, established now).
- **CI:** GitHub Actions — install, lint (ruff + eslint), type-check (mypy + tsc), unit/integration tests, build. Required to pass before merge.

## 13. Testing strategy for Stage 1

- **Backend unit:** password hashing, token issue/verify/rotate, permission resolution, audit writer.
- **Backend integration (httpx + real Postgres):** login happy path, wrong password, expired/invalid token, refresh rotation, RBAC 401/403/200 matrix, user & role CRUD, audit rows written.
- **Migration test:** fresh DB → migrate → assert expected tables/constraints exist.
- **Frontend:** component tests (Vitest) for auth guard and the Users form; a Playwright smoke test for the login → dashboard → create-user flow (introduced here, reused as the e2e harness grows).
- **CI gate:** all of the above run on every push.

No test is deleted or weakened to go green (anti-cheating rules, master prompt §21 of the execution loop). Failures are root-caused.

### Residency & currency model (confirmed approach)

Two distinct concepts, deliberately decoupled:

1. **Residence category** — a per-client / per-quote pricing input (e.g. Kenyan Citizen, East African Resident, Other African Resident, Non-Resident). It selects which **rate tier** the pricing engine uses (park fees, conservancy fees, accommodation, activities all carry per-category rate rows). Categories are configurable and may differ per destination/park — never hard-coded, never assumed identical across parks.

2. **Presentation currency** — the single currency the finished quote is displayed and settled in (KES, USD, EUR, GBP).

**Linkage:** selecting the residence category (by the agent, or by the visitor on the public site via an "Are you a resident or non-resident?" choice) sets both the pricing tier and a **default presentation currency** (Citizen/Resident → KES, Non-Resident → USD, both configurable). The agent may override the currency per quote.

**Computation:** each cost line is calculated in its own source currency, then converted to the quote's presentation currency by the `ExchangeRateProvider` (admin-set manual rates first, live FX API later). Internal costing may be multi-currency; the client always sees one currency. Internal cost/margin are never exposed to client-facing roles (schema-level separation).

*Foundation impact:* confirms the money rule (`NUMERIC`/`Decimal` + explicit currency code per amount, never floats) and reserves `residence_categories` + FX/rate-tier seams for Stage 2. No base "reporting currency" is hard-coded; reporting currency is an `app_settings` value (default USD for internal margin reporting), independent of any quote's presentation currency.
